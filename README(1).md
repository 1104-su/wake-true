# 真醒（WakeTrue）— 项目文档

> 工作名称，暂定。用 JTBD 框架重新定义"起床困难"这个问题，并由此推导产品需要的功能。
> 依据课程 `1-mindset/ch01`（JTBD）与 `ch02-1`、`ch02-2`（逆向思维、失败模式）。

---

## 一、核心洞察（支点）

闹钟的终止条件是一个**瞬时动作**，而"起床"是一个**持续状态**。

瞬时动作可以在零认知负荷下完成——人根本不需要醒。所以闹钟被"雇佣"来做"确保我按时清醒"这件事，实际只交付了"响铃"，把"我是否真的醒了"的验证责任推回给了睡梦中的用户。任务没完成，闹钟就被解雇了（关掉继续睡，然后用户怪自己没毅力）。

**解法方向不是"把关闭动作做难"，而是把终止条件从瞬时动作改成持续状态。**

怎么落到功能上：

| 功能 | 做了什么 |
|---|---|
| F2 移除 App 内关闭入口 | 让"按一下就结束"不再可能 |
| F3 随机间隔的多次确认 | 终止条件从"一个动作"变成"一段必须保持清醒的时间" |
| F4 未响应即重新响铃、音量递增 | 这段时间必须真的保持响应 |
| F5 起床后抽检 | 完成后 10–15 分钟再响应一次，堵住"确认完又躺回去" |

四条合起来，"起床成功"的判定从"按了按钮"变成"**在约 25 分钟内持续保持清醒和响应**"。

这个洞察同时解释了两件事：

- 为什么"按一下就能处理掉铃声"是致命的——它明确授予了"合法延迟"的许可。
- 为什么数学题闹钟效果有限——它只是把**一个瞬时动作变复杂**（难一点的瞬时动作，仍然是一个动作）；我们要的是**一段时间内的持续响应**，两者不是同一类难度。难度的适应速度很快，时间结构无法被适应。

## 二、问题与归因

### 2.1 现象

先区分两个动作：

| 动作 | 后果 |
|---|---|
| **关闭（dismiss）** | 闹钟结束，不再响 |
| **贪睡（snooze）** | 暂停，几分钟后重响（各厂商默认值不同，常见 5 / 9 / 10 分钟） |

核心问题是：**这两个动作都可以在完全没清醒的状态下完成**。长期如此，用户对"自己处理过闹钟"毫无印象，结果睡过头、迟到、失约，然后自责。

> 不同厂商、不同系统版本下"按电源键"到底触发关闭还是贪睡并不一致，需要在验证阶段用具体机型核实。

### 2.2 归因

| 表层表述 | 判断 |
|---|---|
| "按一下就能关" | 这是**症状**，不是原因 |
| "形成肌肉记忆" | 这是**结果**，不是原因 |
| 真正的根因 | **终止条件是"瞬时动作"，而起床是"持续状态"** |

因此**换手势、换按钮位置是无效的**——新动作一样会被固化。真正要堵的是"处理闹钟的动作可以在未清醒状态下完成"。

## 三、JTBD 任务描述

### 3.1 用户是谁

**主画像**：19–24 岁在校学生或刚入职的职场新人；作息偏晚（常在 00:30–02:00 入睡）；早上有硬性时间点（早八、实习通勤、考试日、赶早班车/航班）；有过至少 3 次"闹钟响过但完全没有印象"的经历；使用 **Android 手机**；独居或室友作息相近。

**为什么不写"全球每个人"**："起床困难"看起来普遍，但"普遍"不等于可以直接当目标用户。群体过宽会导致需求冲突、产品缺乏针对性——这是课程列出的常见错误，也是失败模式"用户群体判断错误"。本项目实际可验证的只有小组几个人，先服务一个能被真实观察到的小群体。

**本阶段排除**：iOS 用户（技术方案不成立）、轮班制工作者、需夜间照料婴幼儿的人、被诊断有睡眠障碍的人（属医疗范畴）。

### 3.2 情境

**早晨闹钟响起的那一刻**——半睡状态、认知能力显著低于清醒时、主观上强烈想继续睡。
补充情境（睡前轻接口）：**前一晚准备睡觉、伸手去拿手机的时候**。

### 3.3 要完成什么任务

在目标时间点**真正清醒，并且离开床**。

### 3.4 三层任务

| 层次 | 内容 | 是否可省略 |
|---|---|---|
| **功能任务** | 起床后不会因为困意又躺回去；早晨的时间点不再靠意志力保证 | 不可省略 |
| **情感任务** | 不再因为睡过头而迟到、失约、自责；重新获得对早晨的掌控感 | **不可省略**——只做惩罚会引发对抗情绪 |
| **社会任务** | 在同学、同事、朋友眼中是"说到做到、守时靠谱"的人 | **可以延后**（增值层） |

### 3.5 目前的替代方案

| 方案 | 为什么不足以完成任务 |
|---|---|
| 系统闹钟 + 贪睡按钮 | 处理铃声是**瞬时动作**，零认知负荷；贪睡还授予"合法延迟"的许可 |
| 数学题 / 拍照闹钟（如 Alarmy，同一 App 的两种模式） | 仍然是**一个瞬时动作**，只是变难；重复同一道题反而更快被固化；拍照对着床头柜也能过 |
| 物理闹钟放在房间另一头 | **真正管用**，但需额外买一个，且吵到同住的人 |
| 智能手环震动唤醒 | 舒适，但**不解决"起来之后又躺回去"** |
| 让家人/室友叫醒 | 有效，但不可持续、是社交负债、独居者不可用 |

**共同缺陷**：几乎都在提高**一个瞬时动作**的难度（可以被适应），或依赖**外部人力**。

**痛点一句话**：用户可以在"没有醒"的状态下就让铃声停下来，而系统在那一刻无法区分"他醒了"和"他翻了个身"。

### 3.6 重新表述（4 + 2 模板）

> 当 **作息偏晚、早上有硬性时间点、且经常在半睡状态下处理掉闹钟继续睡的年轻人** 在 **早晨闹钟响起的那一刻**，
> 他们想要 **让自己在目标时间点真正清醒并离开床，而不只是把铃声停下来**，
> 以便于 **不再因为睡过头而迟到失约、不再自责，重新获得对早晨的掌控感，在别人眼里成为一个守时靠谱的人**。
>
> 目前他们的替代方案是 **系统闹钟配合贪睡按钮（部分人叠加数学题闹钟类 App）**，
> 但这个方案的问题是 **处理铃声是瞬时的、零认知负荷的动作，可以在完全没清醒的状态下完成；贪睡按钮还明确授予了"合法延迟"的许可，导致用户以为自己起了床，实际仍在睡**。

## 四、功能推导与优先级

### 4.1 推导链条

```
现象：按键就能停止或延后铃声，半睡状态下处理掉闹钟
  ↓ 归因
根因：处理闹钟是"瞬时动作"，起床是"持续状态"
  ↓ 任务
任务：在目标时间点真正清醒，并且离开床
  ↓ 原则
原则：终止条件必须是"持续状态"
  ↓ 功能（核心机制四条）
F2 移除关闭入口 → F3 随机间隔确认 → F4 未响应重响 → F5 起床后抽检
  ↓ 情感补齐
F6 连续起床天数：让用户看见自己在赢，而不只是被惩罚
```

### 4.2 功能清单

| # | 功能 | 任务层 | 要点 | 优先级 |
|---|---|---|---|---|
| F1 | 一次设置、次日生效的闹钟 | 功能 | 交互不超过 2 步。这是**前提条件**，有学习成本用户第一晚就不会用 | P0 |
| F2 | 响铃后不可一键终止 | 功能 | App 内无任何关闭入口，封死返回键与 App 内退出路径。**四条拦不住的路径**（长按电源键关机、Home 键、强停、卸载）不追求堵住，改为记录并在次日呈现代价 | P0 |
| F3 | 随机间隔的多次确认 | 功能 | 3 次确认，间隔约 60 秒 / 3 分钟 / 8 分钟并随机抖动，累计跨度约 **12 分钟**。随机间隔使固定序列无法被固化 | P0 |
| F4 | 未响应即重新响铃、音量递增 | 功能 | 不重置已完成进度（避免一次失败就放弃），但记录失败计数 | P0 |
| F5 | 起床后抽检 | 功能 | 完成 3 次确认后，10–15 分钟内随机抽检一次，未响应即重新响铃。**没有它，"离开床"这一半就没有机制承载** | P0 |
| F6 | 连续起床天数（streak） | **情感** | 服务情感层的核心功能。中断后**保留最高纪录**，否则用户容易破罐破摔 | P0 |
| F7 | 睡前入口 | 功能 + 情感 | 引导"把手机放到够不着的地方"（唯一真正管用的物理手段）；记录计划入睡时间，为 F9 供数据。是**引导**不是强制，不能替代 F5 | P0 |
| F8 | 赖床记录与难度自适应 | 功能 | 记录**四类**事件（强制终止、确认超时、中途退出、已知绕过）；赖床越多次日越难。与 F6 共用同一份数据 | P1 |
| F9 | 睡眠时长 → 唤醒强度 | 功能 | **未验证假设，不能当结论**：温和唤醒可能更容易起来，也可能根本叫不醒。须 A/B 验证后才决定保留与否 | P1 |
| F10 | 社交解锁码 | **社会** | 监督人设码、App 不存码。**响铃状态下无任何路径可关闭或跳过**；关闭只能在非响铃状态下由监督人确认解除。依赖朋友在线，不能作为唯一通路 | P1 |

> **P0 共 7 条**。课程要求核心功能 3–5 个，这里超出是因为 F1 是前提、F6 是情感层补齐、F7 是前置环节——真正的**机制类功能是 F2–F5 四条**。

### 4.3 不做清单

| 不做 | 理由 |
|---|---|
| 智能唤醒（浅睡期唤醒） | 需整夜监测，成本高，**且根本不解决"关掉继续睡"**——它是"更好地叫醒"，不是"确保真的起来" |
| 白噪音 / 助眠视频 / 助眠音乐 | **另一个 Job**（让大脑安静下来入睡），情境不同（睡前 vs 早晨），市场已被潮汐、小睡眠、Calm 占据。做它等于把第二个 App 塞进来 |
| 社交排行榜、好友 PK | 起床是私事，公开排名增加压力，反而促使用户逃避 |
| 多设备同步、云端账号 | 单人单机场景没有真实需求，徒增成本 |
| 主题皮肤、睡眠数据报表 | 与核心任务无关；数据只作为 F9 的输入存在，不需要呈现层 |
| iOS 版本 | 技术方案不成立，首版不做 |

## 五、失败风险分析

假设 3 个月后项目已经失败了。按 **需求 / 技术 / 场景 / 习惯** 四类追溯原因。

### 5.1 失败原因（17 条）

**需求层面**
1. 只堵住"停止铃声"，没堵住"绕过 App"——长按电源键关机、Home 键回桌面、强停、卸载
2. 功能膨胀：曾打算把助眠内容并排做进来，两个 Job 都做不好
3. 没有"不做清单"，智能唤醒这类"看起来更酷"的功能拖走开发时间
4. 把 F9"睡眠时长 → 唤醒强度"当结论用，实际是未验证假设，结果温和音量根本叫不醒人

**技术层面**
5. 闹钟在后台被系统杀死，**根本不响**——发生一次就足以让用户彻底弃用
6. **iOS 上核心机制不成立**：拦不住用户划掉通知或静音
7. 静音 / 勿扰的假设写反了：Android 勿扰**默认放行闹钟类通知**；iOS 的 Critical Alerts 需向 Apple **单独申请 entitlement 并获批**，不是适配一下就能拿到
8. 锁屏下确认界面难弹出；若要求输入随机数字则必须先解锁——**一旦解锁，"强停 / 进设置"这条绕过路径又打开了**，与 F2 互相矛盾
9. 响铃时用户直接卸载 App——无任何机制可以阻止

**场景层面**
10. 目标用户写成"全球每个人"，实际只服务小组几人，需求从未被验证
11. 第一晚忘记设置或忘记开启，产品从未开始被使用
12. 用户手上已有系统闹钟，**零迁移动力**
13. 同住的人被反复响铃打扰，用户自己把机制关掉了
14. 只在有早八的工作日用，周末不用，连续天数频繁中断
15. 无法在真实睡眠条件下验证效果，**没法向任何人证明它有效**

**习惯层面**
16. 三分钟热度，第二周自己就不用了
17. 社交解锁码依赖朋友配合，朋友不配合机制就废了

> 第 5 条还有一层**国产 ROM 的厂商策略**根因：小米、华为、OPPO、vivo 的自启动管理、后台冻结与省电策略远比原生 Android 激进，需手动加入自启动与后台运行白名单；还要处理**重启后闹钟是否恢复**（`BOOT_COMPLETED`）。**在原生 Android 上 demo 通过，不代表在国产 ROM 上通过。**

### 5.2 评估与预防

**判据**：可能性 高 >70% / 中 30–70% / 低 <30%；严重性 高 = 一旦发生项目基本失败。

**5 个 ⚠️ 高风险**：

| # | 失败原因 | 可能性/严重性 | 预防措施 |
|---|---|---|---|
| 5 | 后台被杀（含国产 ROM、重启不恢复） | 高/高 | 写业务代码**之前**先做技术验证：精确闹钟 + 前台服务 + 电池白名单 + 国产 ROM 自启动白名单 + 重启恢复。验收要覆盖"重启一次 + 放一夜 + 低电量" |
| 1 | 绕过 App | 高/高 | 封死 App 内与返回键路径；四条拦不住的路径**不追求堵住**，改为记录代价 |
| 10 | 需求未验证 | 高/高 | 收窄到 10 位可触达的同学/同事先做访谈。**访谈未完成不进入开发** |
| 11 | 第一晚忘设 | 高/高 | 首次启动引导**只做一件事**——设置明天早上的闹钟，并给出"已生效"确认 |
| 12 | 迁移动力低 | 高/高 | **不要求用户放弃系统闹钟**，允许双闹钟并存，定位是"加一层保险"而非"换个闹钟" |

**其余 12 条**（⚡ 建议解决 / ✓ 考虑解决）：范围失控、锁屏交互、连续天数中断、三分钟热度、勿扰假设、F9 错误假设、无法验证、助眠膨胀（已移除）、打扰同住者（已限定用户）、监督人不配合（已默认关闭）、响铃时卸载、iOS 不可行（已限定平台）。

### 5.3 早期预警信号

| 信号 | 动作 |
|---|---|
| 出现任何一次"闹钟没响" | 停止新功能开发，全部转入可靠性修复 |
| 项目组成员自己连续 3 天不用它 | 做一次完整的失败原因复查 |
| 访谈对象中愿意继续用的比例低于一半 | 重新审视任务定义——可能问题根本不成立 |
| 连续 2 周没人触发过抽检（F5） | 机制可能没生效，或被整体绕过 |
| 强制终止 / 强停占比持续偏高 | "绕过成本"没抬起来，需重新设计代价机制 |

### 5.4 三条不可动摇的设计原则

1. **可靠性 > 功能丰富度**。闹钟不响一次，其他做得再好都没有意义。
2. **把绕过的成本抬到高于起床的成本**，而不是追求"让绕过不可能"——后者做不到，追求它会浪费掉全部开发时间。
3. **不与系统闹钟竞争，做叠加的保险层**——这决定了用户第一晚愿不愿意打开它。

## 六、验证计划

以下都是**尚未验证的假设**。开发前先验证，否则会重蹈失败模式"场景假设错误"。

| 要验证的假设 | 方法 | 对象 | 判断标准 |
|---|---|---|---|
| 目标用户确实有"响过但没印象"的经历，且频率不低 | 用户访谈（问行为，不问意见） | 10 位符合主画像者 | ≥ 6 人近一个月出现 ≥ 2 次 |
| 处理闹钟确实是无意识的（而非明知故犯） | 深度访谈：「最近一次闹钟响时你在想什么？」 | 同上 | 多数人描述为"记不清""手自动就点了" |
| 用户愿意接受"响铃后不能立即关闭" | 原型测试 | 5 位目标用户 | 问行为意愿，不问"你觉得好不好" |
| **保持一段清醒时间就能防住半睡状态的处理动作**（F3/F5 前提：F3 单独约 12 分钟，连同 F5 约 25 分钟） | 项目组连续使用 **14 天**并记录日志 | 项目组 | 半睡状态下无法完成的比例明显高于系统闹钟 |
| **半睡状态下很难联系到监督人**（F10 前提） | 访谈 + 自测 | 同上 | 该说法成立才保留 F10 |
| **睡眠不足时温和唤醒比粗暴唤醒更容易让人起来**（F9 前提，**存在明确反例**） | A/B 对比两种唤醒强度 | 项目组 | 温和组成功率显著更高才保留 F9，否则删除 |
| 不同机型上"按电源键"的实际行为 | 真机核实 | 组内可用机型 | 记录机型 + 系统版本 + 实际触发的是关闭还是贪睡 |

**访谈提问示例**："你最近一次早上被闹钟叫醒是什么时候？当时你是怎么处理的？""当时有没有想过继续睡？后来呢？""你现在怎么保证自己不出错？"
